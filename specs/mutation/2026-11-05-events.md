- Environment: local Docker Compose stack via `.env` (`APP_ENV=local`, `http://127.0.0.1:8080`), rate limit fine.
- Project: `chromium-desktop`. Working tree includes the uncommitted map spec.
- The runner audits one spec per run (default `events.ui.acceptance.spec.ts`), so each spec was run with `--spec`. Baselines were green for all four.

**Union over the three specs that read real data, `bjjevent` mutants only (52):** 30 killed, 20 survived, 2 no-op.
Raw 30/50 = **60%**. Adjusted (killed / (killed + gaps + owned-by-API) = 30 / (30 + 7 + 1)) = **79%**.

Does the corruption reach the map view? Yes. The map loads the same `GET /api/v1/bjjevent` list, and the mutant changed 3 to 11 map-spec responses per mutant. Killed only by the map spec: `location.coordinates.coordinates` mangle, `location.venue` mangle, `name` mangle (and the structural ones). Limits:

- The two mocked scenarios (unmapped notice, truncation notice) call `mockBjjEvents`, whose route wins over the mutation route, so they are unaffected.
- The Cork-narrowed scenarios return one event, so every `rotate` mutant is an identity there. Only the unfiltered `goToMap` scenarios (filter round trip, empty search) see more than one event, and they assert no pins.
- The runner also enumerated `gym`, `competition` and `store` mutants in the map run (102, of which 97 survived and 5 were no-ops). Those lists come from the app shell, not the events map. They are out of scope for the events score and are ignored below.

## Gaps (ranked by visitor impact)

### 1. Map popup: address, directions link, event link, types and dates are never read

- Mutants (map spec): `location.address` rotate/mangle, `location.coordinates.latitude`/`longitude` rotate/mangle, `eventUrl` rotate/mangle, `types` rotate/mangle, `schedule.startDate`/`endDate` rotate/mangle.
- The list specs kill the address, link and type mutants on the card, but the popup is a separate component and has its own reader only for `event-map-popup-venue` and `event-map-popup-event-name`.
- Visitor impact: a wrong "Get Directions" target (Google Maps `query=lat,lon`), a wrong "More Information" link, a wrong address, type or date in the popup.
- Rendered popup (Cork seminar): venue, address (`event-map-popup-address`), Get Directions (`event-map-popup-directions-link`, href `https://www.google.com/maps/search/?api=1&query=51.8998,-8.468`), event name, types (`event-map-popup-event-types`), dates (`event-map-popup-event-dates`, "14 November 2026"), More Information (`event-map-popup-event-link`).
- Fix: add those test ids to `POPUP_TEST_IDS` in `src/ui/pages/events/events.constants.ts`. In `src/ui/pages/events/events-map.page.ts` extend `expectPopupFor` (or add `expectPopupDetails`) to assert the address, the directions href, and per event the types, the link href and the date. Expected values come from `eventCardFromDto` (address, `mapUrl`, `moreInfoUrl`, type badge). Use them in the existing keyboard test ("Then its details are shown") and in the scenario below.

### 2. Unfiltered map: pin to event association and pin position are unasserted

- Mutants: `location.venue` rotate, `location.coordinates.coordinates` rotate, `name` rotate (map).
- The map tests that use real data are all narrowed to Cork (one event), and the unfiltered ones assert only the view switch. A pin named for the wrong venue, or placed at another event's coordinates, passes.
- Fix (new scenario in `events-map.ui.acceptance.spec.ts`): `visitor should see each venue's events when opening its pin on the unfiltered map`. Open `goToMap()`, then for each `pinsFor(SEEDED_UPCOMING_EVENTS)` venue call `openPinWithKeyboard(venue, eventCount)` and `expectPopupFor(venue, namesOfThatVenue)`. Seeded venues are in `seeded.ts`, and these seeded events are always within the 100 limit.
- Pin position: `coordinates.coordinates` rotate survives because no reader exposes where a pin is drawn. Candidate: add `EventsMapPage.expectPinWestOf(a, b)` using `boundingBox()` (Cork pin is left of the Dublin pin). This is geometry, so a lower-value check. Scenario: `visitor should see the Cork pin west of the Dublin pin on the map`.

### 3. Header total for the unfiltered list is checked with a regex only

- Mutant: `total-plus-one` (survived in the events and filters specs). The visitor sees "Found 7 events." for 6 events (confirmed by replaying the mutant on `/events`: `Found 7 events.`; with `?county=Cork` it shows `Found 2 events.`).
- Why no test failed: search is client side, so the exact `Found 1 event.` assertion uses the filtered length. The unfiltered assertions are `/^Found \d+ events\.$/`, because environments hold full datasets.
- Fix: in `events.ui.acceptance.spec.ts`, test "visitor should see only events from the chosen county when filtering by county", add `await eventsPage.expectHeaderTotal('Found 1 event.')` after `expectResultCount(1)` (Cork has exactly one seeded event; `?county=Cork` renders totalItems). Also in the "header count match" test, replace the regex after clearing the search with a check against the card count when the listing fits one page, or keep the regex and accept the residual.

### 4. Event dates on the card and popup are never asserted for real data

- Mutants: `schedule.startDate` and `schedule.endDate`, rotate and mangle (events, filters, map).
- Visitor sees "14 November 2026" on the card (`event-card-schedule`) and in the popup. A day off survives.
- Why: seeded dates are relative to seed time, so `ExpectedEventCard` omits `schedule` and `stripSessionDate` removes the date from session lines. The dates spec proves the Irish-time conversion, but with a mocked body.
- Fix: in `src/ui/pages/events/events.card.mapper.ts` add `schedule` to `ExpectedEventCard` and format `event.schedule.startDate`/`endDate` in Europe/Dublin (`D Month YYYY`, with the range form the card uses). The DTO must come from a source the browser mutation cannot touch (an `eventsApi` client call in the test, not the page's network response). Candidate scenario: `visitor should see an event's dates as the API holds them`. Until then this is low-confidence.

## Tests that do not prove their title

- `visitor should see the header count match the events a search finds` (events spec): the full-listing half asserts only `/^Found \d+ events\.$/`, so `total-plus-one` passes. The filtered half is real.
- `visitor should see pins for the current results when switching from the event list to the map` (map spec): "current results" are one Cork event. Dropping, rotating or mangling the other events' data cannot fail it, and it only checks the venue string, not where the pin is drawn.

No test with a "card shows the X" title let a mutant on X through; name, type, county, address, organiser, pricing, sessions, links were all killed in the list specs.

## Owned by API

- `reverse` (all three specs): order is the API's rule, owned by `events.api.acceptance.spec.ts` "client should receive events ordered by creation date". The UI renders API order (confirmed: the first cards change under the mutant).

## Equivalent (checked against the rendered card and popup)

- `calculatedCosts` rotate/mangle, `description` rotate/mangle, `imageUrl` rotate/mangle, `isActive` mangle, `location.coordinates.placeName` rotate/mangle, `status` rotate: the card text and HTML (no `img`, no inline style, only aria-hidden decoration) and the popup HTML show none of them, and the card never filters on them.
- `location.venue` rotate/mangle on the list card: the card has no venue (the address is shown). The map is where venue matters (gap 2).
- On the map only: `county`, `organiser.*`, `pricingOptions`, `schedule.kind`, `schedule.sessions`, `name` mangle: not in the popup. They are killed in the list specs.
- No-ops (identical values): `isActive` rotate, `location.coordinates.type` rotate.

## Out of contract

- `location.coordinates.type` mangle, `status` mangle: enum values the OpenAPI contract forbids; the app ignores them.

## Questions for the product owner

- `status` (Upcoming, RegistrationOpen, and others such as cancelled) and `isActive` are sent but never shown. Should a visitor see that an event is cancelled or registration is closed?
- `description` and `imageUrl` are never shown on the list card or the popup. Intentional?
- `calculatedCosts` is never shown; the card computes its own price.

## Not run

- The phone map test (`visitor should see the map fit the screen on a phone`) is `@mobile`, so it did not run under `chromium-desktop`. It reads no list data, so the audit could not score it differently.
- No errors or crashes: all four baselines were green and every mutant run completed.
