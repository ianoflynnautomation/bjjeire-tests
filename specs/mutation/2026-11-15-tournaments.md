## Measurement blind spot (read first)

`mutation.mock.ts` only matches list responses (`/api/v1/<resource>` with `data` and `pagination`). The tournament **detail** response (`/api/v1/tournament/<slug>`) is never mutated. So everything the details spec asserts that comes only from the detail endpoint (fee, registration window, registration message, places, divisions, address) is unmeasured. The "Equivalent" verdicts below are only about the list card and list payload. Do not read them as "the details page is protected".

## Gaps (ranked by visitor impact)

### 1. Card date is never asserted (wrong date shown) - Gap: unasserted

- Mutant: `tournament:mangle:date` (survived in both specs; `rotate:date` is a no-op because all seeded dates are 2035-06-02).
- Visitor sees: the card date (`tournament-card-date`, `formatDate(tournament.date)`) a day out, e.g. "3 June 2035".
- Why no test failed: `getTournamentCardData` already reads `date`, but `ExpectedTournamentCard` and `tournamentCardFromSeeded` omit it, and no step passes `date` to `expectCardData`. The title "visitor should find a published tournament in the tournament list" claims venue and fee only, so this is a gap, not a lying title.
- Fix:
  - `src/ui/pages/tournaments/tournaments.card.mapper.ts`: add `'date'` to the `ExpectedTournamentCard` key union and `date: longDay(tournament.day)` in `tournamentCardFromSeeded` (`longDay` lives in `tests/features/tournaments/dublin-time.ts`; the app's `formatDate` renders day, month name, year in Irish time. Confirm the month is long-form on first run; if the card says "Jun", write the short form instead of reusing the app formatter).
  - `tournaments.ui.acceptance.spec.ts`, test "visitor should find a published tournament in the tournament list": extend the "Then the seeded tournament is listed with its venue and entry fee" step to "its date, venue and entry fee" and pass `date: seededTournamentCard.date`. Spec file `specs/features/tournaments.md` title must change in step (spec:check).
  - Since the day is mutable by one day only, one card is enough.

### 2. List header total is never read - Gap: unread

- Mutant: `tournament:total-plus-one` (survived in both specs).
- Visitor sees: "Found N tournaments" (`tournaments-page-header-total`, rendered when total > 0 from `pagination.totalItems`) one too high.
- Why no test failed: `TEST_IDS.headerTotal` exists in `tournaments.constants.ts` but `tournaments.page.ts` has no reader; events and competitions pages have `expectHeaderTotal`.
- Fix: add `expectHeaderTotal(total: string)` to `src/ui/pages/tournaments/tournaments.page.ts` (same body as `competitions.page.ts` line 37, `toHaveText` on `TEST_IDS.headerTotal`). Candidate scenario (or extra step in the divisions-card test): `visitor should see how many tournaments were found when searching the tournament list`: search "Acceptance Closed", expect result count 1 and header total "Found 1 tournament" (copy from the app's `pageTitle.foundPrefix`/`foundSuffixSingular`; put the wording in `tournaments.constants.ts`). Searching all three ("Acceptance") gives "Found 3 tournaments" and is data-dependent on the environment's other tournaments, so prefer the filtered form.

## Tests that do not prove their title

None found. Title claims match what is asserted (name, venue, fee, state, division count on the list; day, venue, fee, window, state, groups on the detail). The only caveat is that the details spec's fee, window and groups cannot be measured by this tool (blind spot above).

## Owned by API

- `tournament:reverse` (survived in both specs; all UI assertions go through a name search so order never matters). List order is an API rule. Note: `tournaments-switched-on.api.acceptance.spec.ts` has "client should get consecutive tournaments on consecutive pages when paging one at a time" but nothing asserts a defined order. Proposed API scenario: `client should get tournaments in ascending date order when listing tournaments` (needs the order rule from the API spec in bjjeire-java; with all three seeded days equal it needs a tie-break stated, so it may need a seed with distinct days first). No UI check proposed: the UI does not reorder.

## Equivalent (list card and list payload)

Evidence for all: `bjjeire-java/src/bjjeire-app/src/features/tournaments/components/tournament-card.tsx` renders only name, registration badge, date, venue name, fee, division count and a link to the slug; no other field.

- `tournament:rotate:competitorLimit`, `tournament:mangle:competitorLimit`, `tournament:mangle:placesTaken`: card does not render them (only the details page, `tournament-details.tsx`, which reads the detail endpoint). Product question 2.
- `tournament:rotate:registrationOpensAt`, `rotate:registrationClosesAt`, `mangle:registrationOpensAt`, `mangle:registrationClosesAt`: card does not render the window; the badge uses `registrationState`, not these instants.
- `tournament:mangle:venue.address`, `venue.coordinates.coordinates`, `.latitude`, `.longitude`, `.placeId`, `.placeName`, `.type` (7): card renders `venue.venue` only.
- 13 no-ops (identical values across the three seeded tournaments or never read): `rotate:` currency, date, entryFeeCents, placesTaken, status, venue.address, venue.coordinates.{coordinates,latitude,longitude,placeId,placeName,type}, venue.venue. All three seeds share date, venue, fee and currency, so rotation cannot differ. This also weakens the kills: a card that showed another tournament's venue or fee would not be caught. Optional hardening: give one seeded tournament a different fee or venue in the app seed.
- 52 `bjjevent:*` mutants (run 1): events loaded by the app shell on `/`; the tournaments spec asserts no event data. Owned by the events feature specs.

## Out of contract

- `tournament:mangle:status` (survived): mangling the enum to a text value the OpenAPI contract forbids. A kill would be robustness, not adequacy. See product question 1 for the real behaviour.

## F3-contaminated (not scored)

- `tournament:rotate:divisionCount` survived in both specs. Seeds all say 5; the only change in the response is live `acceptance-closed` (4 divisions, finding F3) swapping with the others, and no test reads the Closed card's division count. Once F3 is fixed, rotation is a no-op by identical values. No action beyond fixing the data.

## Killed (14, for the record)

`drop-first`, `drop-last` (details only), `duplicate-first`, `empty`, `mangle:currency`, `rotate:name`, `mangle:name`, `rotate:slug` and `mangle:slug` (details only: opening a card follows its link), `mangle:divisionCount`, `mangle:entryFeeCents`, `rotate:registrationState` and `mangle:registrationState`, `mangle:venue.venue` (list only).

Observation: the list spec has no test that follows a card link, so card link targets are only protected by the details spec. Not a gap while both specs run together.

## Questions for the product owner

1. The badge shows "Cancelled" or "Finished" when `status` is CANCELLED/FINISHED and the registration state otherwise (`registration-state-badge.tsx`). All seeded tournaments are PUBLISHED, so no test (UI or this audit) sees that behaviour. Is a seeded cancelled tournament wanted so the list proves it? Candidate scenario: `visitor should see a cancelled tournament marked as cancelled in the tournament list`.
2. The API sends `competitorLimit` and `placesTaken` in the list, but the card never shows places left, and the badge has a `FULL` colour with no `FULL` label in `REGISTRATION_STATE_LABELS`. Should a full tournament show on the card?
3. The card does not show when registration opens or closes. A visitor sees only "Not open yet". Intended?
